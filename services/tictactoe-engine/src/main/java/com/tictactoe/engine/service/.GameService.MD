# GameService

The engine's central orchestrator and the sole authority on game rules for the whole system. It ties together `GameStore` (persistence), `MoveValidator` (rule enforcement), and `GameOutcomeEvaluator` (win/draw detection) to implement the three operations `GameController` exposes: creating a game, reading its state, and applying a move.

## Key Components

- `@Service` - Registers this as a Spring service bean, the single collaborator `GameController` depends on.
- `GameService(GameStore, MoveValidator, GameOutcomeEvaluator)` - Constructor injection of all three collaborators.
- `createGame(String gameId)` - Creates an empty board, persists it via `GameStore.create`, and returns a `CreateGameResponse`. A repeated call for an existing id silently resets that game (no "already exists" check).
- `getGame(String gameId)` - Loads the game and returns a `GameResponse` with the board re-encoded as a single string via `BoardUtils.convertToString`.
- `applyMove(String gameId, MoveRequest move)` - Loop of up to `MAX_ATTEMPTS` (3) attempts. Each attempt loads the game fresh, validates the move via `MoveValidator`; if invalid, returns immediately with the unchanged board and the resulting `StepStatus` (no persistence). If valid, applies the mark, resolves the outcome via `GameOutcomeEvaluator`, and persists via `GameStore.compareAndSave`. A `true` return produces the authoritative `MoveResponse` immediately. A `false` return means another move committed first — the loop re-reads and re-validates rather than retrying the write blindly, so a losing caller gets the honest rejection (`CELL_OCCUPIED`/`OUT_OF_TURN`) on the next iteration. Exhausting all attempts throws `ConflictException` (`ErrorCode.CONFLICT`, 409) rather than returning a made-up status. See `docs/adr/0003-optimistic-concurrency-on-moves.md`.

## Usage Example

```java
CreateGameResponse created = gameService.createGame(gameId);
MoveResponse response = gameService.applyMove(gameId, new MoveRequest(Symbol.X, 4));
```

`GameController` delegates directly to these three methods; `GameService` is where board mutation, rule validation, and outcome resolution are wired together, keeping the controller free of any game logic. `applyMove` itself carries no `@Transactional` — only the compare-and-swap `UPDATE` inside `GameJpaRepository` does — so a losing attempt's re-read always sees the winner's committed write.
