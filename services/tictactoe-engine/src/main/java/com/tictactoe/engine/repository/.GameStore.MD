# GameStore

The repository-facing service that `GameService` talks to instead of touching JPA directly. It exposes exactly the two touchpoints `applyMove` and friends need — `load` and `save`/`create` — so `GameService` never sees `GameEntity`, `GameJpaRepository`, or `UUID`. `save` reuses the exact entity row a prior `load` fetched, avoiding a redundant `findById` and collapsing what would otherwise be two reads and one write into one read and one write.

## Key Components

- `@Component` - Registers this as a Spring bean, the sole collaborator `GameService` needs for persistence.
- `GameStore(GameJpaRepository gameRepository)` - Constructor injection of the JPA repository.
- `load(String gameId)` - Fetches the `GameEntity` by id (via `toUuid`), throwing `GameNotFoundException` if absent, and wraps it in a `Game`.
- `create(String gameId, List<String> board)` - Builds a new `GameEntity` with `GameState.IN_PROGRESS` and the given board, and saves it.
- `save(Game game, List<String> board, GameState state)` - Mutates the `GameEntity` already wrapped inside `game` (obtained from a prior `load`) with the new board/state and saves it, without a second `findById`.
- `toUuid(String gameId)` - Parses a game id string into a `UUID`, throwing `BadRequestException` with `ErrorCode.INVALID_GAME_ID` (→ 400) for a malformed id.

## Usage Example

```java
Game game = gameStore.load(gameId);
List<String> board = new ArrayList<>(game.board());
board.set(position, symbol.name());
gameStore.save(game, board, GameState.X_WON);
```

`GameService.applyMove` loads the game once, computes the new board and outcome, then calls `save` with the same `Game` instance so the update lands on the row already in hand.
