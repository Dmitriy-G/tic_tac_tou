# SimulationRunner

Drives one full simulation run end to end on a dedicated virtual thread: creates the game on the engine, loops moves via `SimulationStep` until terminal, and guarantees the session never ends up stuck `IN_PROGRESS`. This is the class that enforces the CLAUDE.md rule that "every exit path from the simulation loop sets a terminal status, including exceptions and thread interruption" — the `try/catch/finally` structure is built specifically around that guarantee: persist the terminal state, notify subscribers, then release the SSE emitter, always in that order.

## Key Components

- `@Component` - Registers the class as a Spring bean.
- `SimulationRunner(GameEngineClient, SimulationStep, SessionStateWriter, SimulationEventPublisher)` - Constructor injection of all collaborators needed to run a simulation.
- `run(String sessionId, String traceId)` - The simulation entry point invoked on a virtual thread by `SimulationStarter`. `sessionId` doubles as the engine's `gameId`, so no separate simulation id exists anymore. Sets the correlation id in MDC (which doesn't propagate across `Thread.ofVirtual().start()`, so it must be re-applied here), creates the game via the engine client, drives `SimulationProgress` through `SimulationStep.execute` while `hasNextIteration()` holds, persists each returned `MoveRecord` via `stateWriter.recordMove`, and closes the loop-exit hole via `stateWriter.persistTerminal`. On any `RuntimeException`, resolves the error code, logs, marks the session `FAILED` via `stateWriter.fail`, and publishes a failure event. The `finally` block always completes the SSE emitters and clears MDC.
- `codeOf(RuntimeException e)` - Private helper extracting the `ErrorCode` from a `BaseException`, defaulting to `INTERNAL_ERROR` for anything else — defensive against exceptions that aren't the service's own typed hierarchy.

## Usage Example

```java
Thread.ofVirtual().start(() -> runner.run(sessionId, traceId));
```

`SimulationStarter` launches `run` on its own virtual thread right after the compare-and-swap
claims the session (`status: CREATED -> IN_PROGRESS`), so the `/simulate` request can return 202
immediately while the moves play out asynchronously.
